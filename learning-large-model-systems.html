Ascend NPU 大模型系统与性能优化

从 Transformer 和 NPU 执行模型，走到 CANN、推理引擎、HCCL、多卡通信与可复现实验。目标不是记住术语，而是能定位瓶颈、验证假设并交付稳定服务。

先建立正确的学习方式

每次优化都遵循同一条链路：建立基线 → 固定变量 → 找到瓶颈 → 修改一个因素 → 复测延迟、吞吐、稳定性和成本。

性能结论必须绑定模型、硬件、输入输出长度、并发度、软件版本和服务目标。没有这些上下文，“某配置更快”通常不能迁移到另一套环境。

先认清 Ascend 技术栈

运行时层

硬件与 CANN

Ascend NPU、AI Core、HBM、片间互联、驱动与固件构成底座。CANN 提供运行时、算子库、图编译和调试工具；版本必须与 NPU 型号、镜像和框架匹配。

框架层

PyTorch 与 torch_npu

理解设备放置、算子 fallback、动态图与图模式、混合精度和内存分配。遇到异常时先确认算子是否落在 NPU，避免把 CPU fallback 当成 NPU 性能。

服务层

vLLM-Ascend + KServe LLMISVC

掌握模型支持矩阵、镜像和 checkpoint 的对应关系，理解如何通过 KServe 的 LLMInferenceService（LLMISVC）配置 vLLM-Ascend、资源、并行和服务参数。

通信与观测

HCCL 与 NPU Profiling

多卡通信使用 HCCL；采集优先使用 torch_npu.profiler、CANN/msprof 或 MindStudio，记录 NPU kernel、HCCL、内存和算子时间。

阶段学习路线

01第 1–2 周

编程、数学与系统基础

  • Python、Linux、Shell、Git；补齐 C/C++ 的内存、线程、锁和异步执行。
  • 掌握线性代数、概率统计、微积分的必要部分，以及操作系统、网络、数据结构。
  • 理解进程、线程、NUMA、I/O、复杂度和基本并发模型。
02第 3–4 周

深度学习与 Transformer

  • 能解释 Attention、MHA、GQA、RoPE、RMSNorm、MoE 和 Transformer 训练流程。
  • 理解 Prefill、Decode、KV Cache，以及参数、激活、序列长度和 batch 对显存的影响。
  • 手写一个小型 Transformer，用 PyTorch 跑通训练或推理。
03第 5–6 周

Ascend NPU、CANN 与算子执行

  • 学习 AI Core、HBM、片间互联、带宽、算力、算术强度和 Roofline。
  • 掌握 CANN Runtime、算子库、图模式、混合精度、内存分配和算子 fallback。
  • 用 torch_npu 跑通基础算子，确认设备放置、精度和 CANN/驱动/固件版本匹配。
04第 7–9 周

vLLM-Ascend 推理与 LLMISVC 调度

  • 深入 Prefill、Decode、Chunked Prefill、Continuous Batching、PagedAttention 和 KV Cache。
  • 掌握 Ascend 支持的量化路径（BF16、FP16、FP8/INT8 等以具体版本为准）和 Speculative Decoding。
  • 通过 KServe LLMInferenceService 部署 vLLM-Ascend，观察请求队列、NPU 内存、KV Cache 和 batch 调度。
05第 10–11 周

HCCL 与 LLMISVC 分布式执行

  • 理解 TP、PP、DP、EP 的通信量、显存代价、适用场景和扩展边界。
  • 学习 HCCL 的 AllReduce、AllGather、All-to-All、通信拓扑和通信计算重叠。
  • 了解 LLMISVC 的副本、资源、并行参数如何落到 Pod，及其与 Kubernetes 调度、服务路由的关系。
06第 12–16 周

NPU Profiling、LLMISVC 验收与容量规划

  • 使用 torch_npu.profiler、CANN/msprof、MindStudio 和 NPU 监控工具定位瓶颈。
  • 设计固定 workload 的 A/B 实验，观察 P50、P95、P99、错误率和结果稳定性。
  • 通过 LLMISVC 就绪状态、端点请求、日志和 MaaS/压测流量验证服务，再从绝对 SLO 确定容量。

性能指标速查

TTFTTime to First Token，首 token 延迟，常受排队和 Prefill 影响。
ITL / TPOT生成 token 间隔，反映 Decode 阶段的交互体验。
吞吐量tokens/s 或 requests/s，必须注明输入输出 token 口径。
并发度同时处理的请求数；高并发不等于满足用户 SLO。
P95 / P99尾延迟比平均值更能暴露排队、抖动和资源争用。
NPU / HBM观察 NPU 利用率、AI Core、HBM 带宽和显存占用，识别计算与内存瓶颈。
HCCL 时间记录集合通信耗时、链路利用率和通信计算重叠，判断多卡扩展是否有效。

实践项目

项目 1：Ascend 单卡推理基线

  • 在目标 Ascend 型号上部署一个 7B 左右模型，固定 prompt、输出长度和并发档位。
  • 记录 TTFT、ITL、吞吐、P95、错误率、HBM 和 NPU 利用率，并核对 CANN/torch_npu 版本。
  • 比较 batch size、上下文长度和 BF16/已验证量化路径的变化。

项目 2：NPU KV Cache 与算子观察

  • 改变上下文长度和并发度，画出 HBM、TTFT、ITL、吞吐曲线。
  • 阅读 vLLM-Ascend 的 KV Cache、PagedAttention 和调度代码。
  • 用 torch_npu.profiler 或 MindStudio 标出 NPU kernel、算子 fallback 和排队突变点。

项目 3：HCCL 多卡并行 A/B

  • 在相同 workload 下比较 TP、DP，模型适配时再评估 EP/PP。
  • 采集 HCCL 通信时间、链路利用率、HBM、NPU 利用率和扩展效率，不只比较 tokens/s。
  • 输出 NPU 拓扑、镜像、CANN/驱动版本、配置和原始日志，保证结果可复现。

项目 4：KServe LLMISVC 端到端服务化

  • 编写并部署 LLMInferenceService，让 KServe 创建 vLLM-Ascend 工作负载，配置模型、镜像、NPU 资源、并行和服务参数。
  • 验证 CR 状态、Pod/容器日志、就绪探针、服务端点和 MaaS/压测请求，再接入 NPU 监控、限流和故障恢复。
  • 形成包含硬件、镜像、模型、CANN、LLMISVC YAML、指标、图表、结论和限制的性能报告。
