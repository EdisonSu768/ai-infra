阅读方法与状态标签

先问“它解决什么问题”，再记名词。 每个知识点都要能连接到一次请求、一个算子、一段通信或一个服务故障。

性能结论必须绑定模型、Ascend 型号、CANN/驱动、vLLM-Ascend 镜像、LLMISVC 配置、输入输出长度、并发度和服务 SLO。

核心基础当前主流按场景历史/了解即可Ascend 专项

趋势标签按 2026 年主流开源推理栈和本客户的 Ascend + vLLM-Ascend + KServe 链路标记；“历史”表示仍需理解原理，但不应作为默认方案。

问题域总览

模型计算

回答“模型每一层算什么、为什么要这么算，以及权重/激活/KV 占多少内存”。

推理运行时

回答“请求如何排队、批处理、复用 KV，并把 Prefill/Decode 变成高效执行”。

Ascend / CANN

回答“算子如何落到 NPU、哪里发生 fallback、CANN 和 torch_npu 如何影响性能”。

分布式与通信

回答“模型如何跨卡切分，HCCL 通信何时成为瓶颈，以及怎样扩展”。

服务编排

回答“LLMISVC 如何把模型、镜像、NPU 资源和 vLLM-Ascend 组合成可访问服务”。

观测与决策

回答“怎样用 trace、SLO 和实验数据证明优化有效，并确定容量”。

一、模型与计算图

概念解决什么问题需要连带理解状态
Transformer用注意力和前馈网络建模 token 之间的依赖，是当前生成式模型的共同计算骨架。Residual、Norm、Attention、FFN、训练/推理路径。核心基础
MHA / GQA在表达能力和 KV Cache 成本之间取平衡；GQA 用较少 KV heads 降低 Decode 读写。Q/K/V heads、head_dim、KV cache 形状、带宽瓶颈。GQA 主流
MLA进一步压缩 KV 表示，减少长上下文和高并发 Decode 的缓存压力。latent KV、模型 checkpoint 结构、运行时 kernel 和硬件支持。模型相关
RoPE 与长上下文给注意力注入位置信息，并通过 scaling 让模型处理更长上下文。频率、位置插值、YaRN/NTK scaling、实际上下文上限。基础 + 按模型
MoE只激活部分专家，在接近更大参数容量的同时控制每 token 计算量。router、top-k、expert parallel、负载不均、All-to-All。当前主流
MTP / Speculative Decoding用额外预测或小模型一次猜多个 token，减少 Decode 串行步数。draft/verify、接受率、额外显存、模型与引擎支持。当前主流
量化降低权重、激活或 KV 的存储和带宽成本，让模型适配更多 NPU 或提高并发。BF16/FP16 基线、FP8/INT8、INT4、校准、精度回归。硬件相关主流
Tokenizer 与 token 口径决定输入/输出长度、吞吐统计和上下文上限；口径错了，性能结论也会错。prompt_tokens、completion_tokens、服务端 usage、不同 tokenizer。核心基础

二、推理运行时与请求调度

概念解决什么问题需要连带理解状态
Prefill一次处理输入上下文，生成首个 token；通常决定 TTFT 和初始计算峰值。矩阵计算、长 prompt、Chunked Prefill、队列等待。核心基础
Decode逐 token 生成；通常受 KV 读取、内存带宽和串行步数限制。ITL/TPOT、batch、KV layout、MTP。核心基础
KV Cache缓存历史 K/V，避免每个新 token 重算整个上下文。层数、KV heads、head_dim、block、HBM 容量和碎片。核心基础
PagedAttention / 分块缓存按 block 管理 KV，减少连续大块分配造成的碎片，并支持动态请求。block table、分配/回收、prefix block、内存水位。当前主流
Continuous Batching让新请求在已有 batch 的 token 迭代间加入，避免静态 batch 等待最慢请求。scheduler、iteration、chunk、队列公平性和尾延迟。当前主流
Prefix Cache复用相同系统提示、长文档或会话前缀的 KV，减少重复 Prefill。cache key、命中率、租户隔离、路由 locality、失效。当前主流
Chunked Prefill把长 Prefill 切成片段，避免长请求独占设备并阻塞 Decode。chunk size、TTFT/ITL 权衡、调度优先级。当前主流
Prefill/Decode 分离（PD）把上下文计算和 token 生成放到不同资源池，分别扩容和调优。KV transfer、路由、负载均衡、通信代价、会话粘性。复杂场景主流
静态 batching把固定数量请求一次组成 batch，适合教学和规则简单的离线任务。padding、最慢请求、空槽和尾延迟。服务默认已过时

三、Ascend NPU 与 CANN

概念解决什么问题需要连带理解状态
Ascend NPU / AI Core / HBM提供矩阵和向量计算以及模型权重、激活、KV 的高速存储。算力、HBM 带宽、内存容量、片间互联、CPU/NPU 协作。Ascend 专项
CANN Runtime把框架调用转换为 NPU 可执行任务，提供算子、内存和执行队列能力。驱动/固件兼容、算子库、Stream、同步和版本矩阵。Ascend 专项
torch_npu让 PyTorch 模型使用 NPU 设备、算子和自动求导/推理能力。设备放置、dtype、算子支持、fallback、编译缓存。Ascend 专项
动态图 / 图模式动态图便于调试，图模式可减少调度开销并进行编译优化。shape 稳定性、编译耗时、缓存、动态 shape 和精度一致性。按 workload
算子 fallback当 NPU 没有对应实现时保证功能继续运行，但可能把关键路径退回 CPU。日志、同步、数据搬运、算子覆盖率和性能回归。诊断必学
vLLM-Ascend把 vLLM 的调度、KV Cache 和批处理能力适配到 Ascend NPU。版本/镜像、模型支持矩阵、量化、TP/DP/EP、启动参数。客户主线
torch_npu.profiler / msprof / MindStudio采集 NPU kernel、内存、算子和通信 trace，证明瓶颈在哪里。采集窗口、trace 大小、时间线、NPU/HCCL 关联。Ascend 专项
判断顺序：先确认 CANN、驱动、固件、torch_npu 和 vLLM-Ascend 版本匹配，再确认算子真的落在 NPU，最后才讨论 batch、量化或并行调参。

四、分布式并行与 HCCL

概念解决什么问题需要连带理解状态
Tensor Parallel（TP）把一个层的权重或矩阵切到多卡，解决单卡放不下或单卡计算不足。切分维度、通信点、head 可整除、HCCL、跨节点带宽。推理主流
Data Parallel（DP）复制模型到多个实例，让不同请求或 batch 并行处理，提高服务容量。副本数、路由、会话粘性、显存重复、聚合吞吐。推理主流
Expert Parallel（EP）把 MoE 专家分布到不同卡，减少每卡专家权重并支持更大专家池。router、All-to-All、expert imbalance、通信计算重叠。MoE 必需
Pipeline Parallel（PP）按层切分模型，降低单卡显存压力。microbatch、pipeline bubble、调度复杂度、跨节点通信。超大模型场景
HCCL在 Ascend 卡之间执行集合通信，让 TP/DP/EP 协同工作。AllReduce、AllGather、All-to-All、拓扑、链路利用率。Ascend 专项
通信与计算重叠在等待通信时执行可独立的计算，减少通信暴露在端到端关键路径上的时间。stream、异步事件、分桶、trace 时间线、同步点。当前主流
不要背“TP 一定更快”。 TP 是否有效取决于模型形状、卡间拓扑、HCCL 时间、请求长度和 SLO；先做同 workload A/B，再下结论。

五、KServe LLMInferenceService（LLMISVC）

概念解决什么问题需要连带理解状态
LLMInferenceService用声明式资源描述一个生成式模型服务，让 KServe 负责创建和管理工作负载。metadata、spec、模型来源、runtime、资源、并行和 endpoint。客户主线
Runtime / 镜像确定 Pod 中运行哪个 vLLM-Ascend 版本、CANN 依赖和启动入口。镜像架构、digest、环境变量、启动命令、版本矩阵。Ascend 专项
NPU resources向 Kubernetes 声明每个 Pod 的 NPU 数量，保证调度和隔离。requests/limits、节点标签、拓扑、共享和资源冲突。核心基础
并行与副本把 vLLM-Ascend 的 TP/DP/EP 参数和 LLMISVC 的 Pod/副本布局对应起来。总卡数、每 Pod 卡数、DP 组、HCCL rank、扩缩容。客户主线
就绪与生命周期确认模型已加载、端点可用、滚动更新和异常重启不会把流量导入坏 Pod。CR status、readiness、startup、日志、事件、优雅终止。上线必学
端点与 MaaS/压测从真实访问入口验证服务，而不是只看 Pod Running。路由、认证、超时、流式响应、token usage、错误率。交付必学
LLMISVC 验收链：CR 状态 → Pod/容器日志 → NPU 资源与进程 → readiness → 服务端点 → MaaS/压测请求 → TTFT/ITL/吞吐/错误率 SLO。

六、观测、指标与实验

TTFT首 token 延迟；排队、Prefill 和模型加载都会影响它。
ITL / TPOT生成 token 间隔；主要观察 Decode 的稳定交互体验。
P95 / P99尾延迟；暴露排队、抖动、资源争用和长请求影响。
Completed tokens/s已完成请求的 token 吞吐，注明 input/output token 口径。
NPU / HBM识别 AI Core 计算、HBM 带宽、容量和内存水位瓶颈。
HCCL 时间判断多卡收益是否被集合通信和同步抵消。
方法解决什么问题正确用法状态
固定 workload A/B隔离一个变量，避免把模型、硬件、版本和调参混在一起。固定输入分布、输出长度、并发档位、镜像和 LLMISVC 配置。核心方法
torch_npu.profiler / msprof把端到端慢点映射到 NPU kernel、算子或 HCCL 时间线。用稳定窗口采集，区分冷启动、预热、稳态和 trace 开销。Ascend 专项
容量与 SLO回答“在 TTFT、ITL、错误率门槛下能承载多少并发”。用绝对 SLO 的稳定档位判断容量，不能用一次跑分或相对拐点替代。当前主流
只看平均吞吐只能回答理想平均处理量，无法说明用户体验和尾部风险。与 P95/P99、队列、错误率和稳定性一起看。过时用法

七、主流趋势与容易学偏的概念

继续投入
MoE、GQA/MLA、量化

它们直接改变计算量、KV Cache 或权重带宽，是当前 SOTA 模型和高并发推理的主要方向。学习时必须结合具体 checkpoint 和 Ascend runtime 支持，不能只看模型名称。

继续投入
Continuous Batching、Prefix Cache、Chunked Prefill

这些机制把设备从“一个请求跑到底”变成按迭代调度，直接影响 TTFT、ITL、命中率和资源利用率，是 vLLM-Ascend 服务调优主线。

按场景投入
PD 分离、MTP、Speculative Decoding

对长上下文、Agent 或高并发可能很有价值，但需要 KV transfer、模型头、路由和引擎支持。先验证链路，再把它们纳入容量方案。

降级学习
静态 batching、只看平均 tokens/s

仍可用于教学和离线基准，但不适合作为在线 LLMISVC 默认调度或客户容量结论。必须补充尾延迟、错误率和排队数据。

降级学习
CUDA-only profiler、静态显存估算

CUDA 工具和静态 KV 公式有助于理解原理，却不能代替 CANN/NPU trace、真实 HCCL 证据和 vLLM-Ascend 启动验证。

避免默认
先改源码、先定 TP、先追求满载

先用固定版本的原版 vLLM-Ascend 镜像建立基线，确认模型支持和 NPU 落地，再根据 profiler 和 SLO 选择优化动作。

版本意识：状态标签会随模型、CANN、vLLM-Ascend 和 KServe 版本变化。凡是“支持/更快/最优”的判断，都要回到当前 checkpoint、镜像、硬件拓扑和实测证据。

八、按能力组织的实践项目

能力 1：解释一次请求

  • 从 tokenizer、Prefill、KV 写入、Decode 到流式返回，画出请求生命周期。
  • 给每一步标注 CPU、NPU、HBM、HCCL 和队列的作用。

能力 2：定位一次慢请求

  • 在 LLMISVC 固定模型、镜像、输入输出和并发，用 TTFT/ITL/P95 找出异常。
  • 用 torch_npu.profiler 或 msprof 对照 NPU kernel、fallback、HBM 和 HCCL trace。

能力 3：验证一次拓扑

  • 比较 TP/DP，记录每 Pod NPU 数量、HCCL 时间、HBM、NPU 利用率和扩展效率。
  • 把 YAML、镜像 digest、CANN/驱动版本、拓扑和原始日志放入报告。

能力 4：交付一个服务

  • 编写 LLMInferenceService，验证 CR、Pod、readiness、端点和 MaaS/压测流量。
  • 按绝对 SLO 判定稳定容量，并说明未测量或不适用的部分。
