二、推理运行时与请求调度

一次请求如何变成 token？

Prefill核心基础

解决：一次处理输入上下文并生成首 token，主要影响 TTFT；长 prompt 常形成计算峰值。

input lengthTTFTKV write
Decode核心基础

解决：逐 token 生成输出，主要受 KV 读取、HBM 带宽和串行步数影响。

ITL / TPOTbatchMTP
KV Cache核心基础

解决：避免每个新 token 重算历史 K/V；代价是占用 HBM，并需要高效分配、读写和回收。

PagedAttention / 分块缓存当前主流

解决：按 block 管理 KV，减少连续大块分配造成的碎片，并支持动态请求；需要关注分配、回收和内存水位。

解决：按迭代加入和退出请求，避免静态 batch 被最慢请求拖住，提高在线服务利用率。

Prefix Cache当前主流

解决：复用相同系统提示、长文档或会话前缀的 KV，减少重复 Prefill；收益取决于命中率和路由 locality。

解决：把长 Prefill 切成片段，避免长请求独占设备并阻塞 Decode；需要平衡 TTFT、ITL 和调度优先级。

四、并行与通信

模型如何跨多张 NPU？

并行方式速览概念总览
TP:  一层权重切片 -> [卡0][卡1][卡2][卡3] -> 合并结果
DP:  [完整副本 0]   [完整副本 1]   <- 请求路由
EP:  token -> Router -> [Expert 0] [Expert 1] [Expert 2]
PP:  Layer 1..16 -> Stage 0 -> Stage 1 -> Layer 17..32
DCP: Decode KV/context shards -> attention -> gather/reduce
PCP: Prefill token shards -> attention -> restore order

记法：TP/PP 组成一个模型副本，DP 复制副本；EP 主要服务 MoE 专家分布；DCP/PCP 分别切 Decode/Prefill 的上下文工作。

Tensor Parallel（TP）推理主流

解决：把层内权重或矩阵切到多卡，解决单卡显存或计算不足；代价是层间通信。

切分维度head 可整除通信点
Data Parallel（DP）推理主流

解决：复制模型到多个实例，承载更多独立请求；代价是权重和 KV 的重复占用。

副本路由session sticky
Expert Parallel（EP）MoE 必需

解决：把 MoE 专家分布到不同卡；瓶颈常来自 All-to-All 和 expert imbalance。

RouterToken Dispatch负载均衡
MoE 通信按模型/拓扑

解决：把 token 发往对应专家并汇总结果；跨卡时会引入 HCCL All-to-All 和负载不均。

Token DispatchAll-to-AllExpert imbalanceToken Combine
Pipeline Parallel（PP）超大模型

解决：按层切分模型以降低单卡显存压力；代价是 pipeline bubble 和调度复杂度。

microbatchbubble层切分
Decode Context Parallel（DCP）长上下文 Decode

解决：把 Decode 阶段的上下文/注意力工作分摊到多个 rank，再通过集合通信汇总；重点是降低长 KV 读取压力，不能只按卡数线性推断收益。

decode context shardDCP groupAllGatherDCP + MTP
Prefill Context Parallel（PCP）长上下文 Prefill

解决：把 Prefill token/context 切到多个 rank 并行处理，再恢复全局 token 顺序和 attention metadata；需要 padding、slot mapping、KV 和多模态路径共同支持。

prefill token splitPCP metadataAllGather / restorePCP + DCP
HCCLAscend 专项

解决：在 Ascend 卡之间执行集合通信，让 TP/DP/EP 协同工作。

AllReduce:  卡0 --+             +--> 卡0
                   +-- HCCL ----+
             卡1 --+             +--> 卡1
All-to-All:  token 分片 -> 各卡交换 -> 对应专家
AllReduceAllGatherAll-to-All拓扑
通信与计算重叠当前主流

解决：在等待通信时执行可独立的计算，减少通信暴露在端到端关键路径上的时间；需要通过 trace 验证同步点。

七、趋势与取舍

哪些值得重点学，哪些只需理解？

MoE / GQA / MLA / 量化继续投入

原因：它们直接改变每 token 计算量、KV Cache 或权重带宽，是主流模型和高并发推理的重要方向。

checkpoint 结构硬件支持精度回归
Prefix Cache / Chunked Prefill继续投入

原因：它们直接影响长上下文服务的 Prefill 成本、TTFT、KV 命中率和 Decode 稳定性。

cache localitychunk size尾延迟
MTP / Speculative / PD按场景验证

原因：可能减少 Decode 串行步数或隔离 Prefill/Decode，但依赖模型头、KV transfer、路由和引擎能力。

接受率额外显存会话粘性

原因：适合教学和离线任务，但在线服务容易被 padding、空槽和最慢请求拖累。

paddingslowest request

原因：可帮助理解通用原理，却不能代替 CANN/NPU trace、HCCL 证据、尾延迟和稳定性验证。
